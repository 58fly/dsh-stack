# 09 — `npx dsh-stack` 静默零输出：安装形态才会暴露的主模块判断错误

## 动机

0.3.0 发布后做「装完能不能用」的冒烟：新建空项目 `npm i dsh-stack@0.3.0`，跑 `npx dsh-stack status` —— **没有任何输出，退出码 0**。同一份代码在仓库里 `node bin/dsh-stack.mjs status` 输出完整。

也就是说 0.3.0 的核心卖点（一个能救回宿主的命令）在真实安装形态下等于不存在，而且不报错。

## 故障

```js
// 0.3.0 的 bin/dsh-stack.mjs
const isMain = process.argv[1] !== undefined
  && import.meta.url === pathToFileURL(process.argv[1]).href
if (isMain) process.exitCode = main()
```

npm 安装 `bin` 时生成符号链接：

```
node_modules/.bin/dsh-stack -> ../dsh-stack/bin/dsh-stack.mjs
```

- exec 走链接路径 → `process.argv[1]` = `.../node_modules/.bin/dsh-stack`
- node 加载后 `import.meta.url` = `file:///.../node_modules/dsh-stack/bin/dsh-stack.mjs`（已解析的真实路径）

两者永不相等 → `isMain` 为 false → 入口什么都不做，进程正常退出。**没有报错、没有提示**：用户看到的是「命令跑了，但什么都没发生」，比崩溃更难归因。

## 为什么没被发现

所有断言都在仓库内跑，仓库里没有 `.bin/` 这一层 —— 缺陷唯一会出现的位置恰好是唯一没验证过的地方。这是验收姿势的缺口，不是代码覆盖率的缺口。

## 本次做法

1. `isMain` 改比 realpath：

```js
const entry = process.argv[1]
if (entry === undefined) return false
try { return realpathSync(entry) === realpathSync(fileURLToPath(import.meta.url)) }
catch { return false }
```

2. 新增回归断言 `CLI 经符号链接调用时仍会被执行`：临时目录造一个 `.bin/dsh-stack` 符号链接，`spawnSync` 调它，断言退出码 0 且 stdout 含 `dsh-stack status`。
3. `docs/验收清单.md` 加 **E7：从 npm 安装产物里跑一次命令**；`AGENTS.md` 加两条（主模块判断比 realpath、`bin/` 改动必须在安装形态下验证）。

## 验收

```bash
node test/uninstall-guard.test.mjs     # 26 checks passed
npm i dsh-stack@0.3.1 && npx dsh-stack status   # 正常输出
```

先红后绿确认过：把实现改回 0.3.0 的写法，新断言报 `match` 失败；改回 realpath 才绿。

## 教训

4. **仓库内直跑 ≠ 安装后可用**。凡是被包管理器「加工」过的东西（`bin` 的符号链接、`files` 白名单裁剪、`prepublishOnly`、平台的 `.cmd` shim），都必须在真实安装形态下走一遍。`npm test` 全绿对它没有任何证明力。
5. **静默无操作比崩溃更危险**。崩溃会留下堆栈、有人报 bug；零输出配退出码 0 会被当成「这个功能大概就这样」。凡是「什么都不做也算成功」的入口，必须有断言证明它**确实做了事**（这里断言的是 stdout 有内容，不是仅仅退出码为 0）。
6. **发布后立刻做装机冒烟**。这次是发完 30 秒内发现的，代价一个 patch 版本；如果等用户报，代价是「命令没用」这个印象。
