# 04 — 工程文档体系

## 动机

上游零文档。缺陷不是「不好看」，是接手的人（包括三个月后的自己）无法判断：

- 哪些文件是上游内容、哪些是本仓库改的 → 跟上游更新时不敢动。
- 守卫依赖宿主的哪些非公开接口 → 宿主升级后不知道会坏在哪。
- 为什么护栏只有这两个、为什么目录是 `preset/` → 容易「顺手改回去」。

## 做了什么

沿用 `dsh-cn-think` 的**结构**，不沿用它的体量（那个仓库有 Web UI + 多语言 + 客户端生命周期，1100 行发布说明是它的复杂度换来的）：

| 文件 | 给谁看 | 内容 |
|---|---|---|
| `AGENTS.md` | agent | 最高优先级约束：发布铁律、目录规范、技能镜像规则、守卫改动规则 |
| `CHANGELOG.md` | 用户 | 用户可感知变化，随包分发 |
| `README.md` / `README.en.md` | 用户 | 安装、用法、两个守卫、可调字段、边界 |
| `docs/实现说明.md` | 维护者 | 装载链路、文件职责、宿主私有契约表、已知限制 |
| `docs/验收清单.md` | 维护者 | 逐条可打勾，分 A–G 七组 |
| `docs/发布说明.md` | 维护者 | 每版为什么改、复现命令、连带清单、遗留 |
| `docs/decisions/01–04` | 维护者 | 四个决策及「为什么不选另一个」 |
| `issues/01–05` | 维护者 | 每次改动的动机与验收留档 |

**刻意不建**：`docs/research/`（结论已固化进实现说明）、`docs/agents/workspace.yaml`（agent 工作区插件的生成物，本仓库不用那个插件）、`lib/` 与 `client.js`（无运行时代码、无 Web UI）。理由写在 AGENTS.md 的「不建的目录」一段。
