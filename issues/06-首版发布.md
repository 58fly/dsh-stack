## 实测记录（2026-11-03）

```
tag 推送        db2cce6 → refs/tags/v0.1.0
CI publish      run 41630334925 success 14s
npm 打包        41 文件 / 54.4 kB（解包 141.7 kB）
registry        dist-tags.latest = 0.1.0
```

**踩到一个真实缺陷并修掉**：npm staged publishing 会自己写入占位版本 `0.0.0-stage`（描述 `Temporary package placeholder for staged publishing`，无 `repository`，解包仅 331 字节）。它不对应任何 commit，无法补 tag；原 `verify-release.mjs` 把它当真实版本，导致 0.1.0 发布成功后自检立刻变红。已在脚本里加 `NPM_INTERNAL_VERSIONS = new Set(['0.0.0-stage'])` 豁免，命中时打印「npm 内部占位版本，不对应 commit」。修正提交 `dfb9294`。

另记：registry 有 CDN 缓存，发布瞬间查询仍会读到 `latest = 0.0.0-stage`，需加 `?t=<timestamp>` 或等约 45 秒。

## 风险

`dsh-stack` 这个包名在 npm 上可能已被占用。检查到 E404 之外的响应时，两条路：

- 改用 scope：`@58fly/dsh-stack`（同步改 `cordis.patch.yml` 的 include 路径与 `verify-manifest.mjs` 的期望值）
- 换名：如 `dsh-deepseek-stack`

任一都会影响 include 路径这条硬耦合，必须重跑 `npm test`。
