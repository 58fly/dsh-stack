# 08 — 停用/卸载后新建会话失败：把上次的「清残留」变成「修机制」

## 动机

用户报告：DSH 升级到最新版后，安装 `dsh-stack` 插件出现异常，要求做到双向兼容；并且明确要求新增一个能力 —— **同类问题出现后，插件被禁用或卸载不能把 DSH 带崩**。

上一轮排查（会话 `session-19333a62-3c89-475e-9d9b-d2fbb3eed82d`，工作目录 `/Volumes/data/deepseek-stack`）已经定位过同一个问题，但那次修的是**现场**：手工清掉六处残留、改掉 11 个会话档案与 23 份投影缓存。机制没动，所以这次必然复发 —— 这次要修的是机制。

## 先排除的误判

「升级之后才坏」很容易让人归因到 API 漂移。逐条核实后**全部排除**：

| 检查 | 结果 |
|---|---|
| 宿主版本 | `0.2.2-rc.1`（`Contents/Info.plist` 与 asar 内 `package.json` 一致） |
| `engines.dsh >=0.2.1-rc.5` | 满足 |
| 预设引用的 25 个 `@deepseek-ai/*` 包 | 零缺失 |
| 宿主私有契约 | 7/7 PASS（`agent/turn-stopping`、`agent.steer`、`session.snapshotEvents`、工具名、`{{model}}`） |
| 宿主内 cordis 版本 | `4.1.0`，满足 peer `>=4.0.5` |
| 崩溃日志里的 `desktop welcome: Web authentication failed` | 与本问题无关，0.2.1-rc.3 时期既有 |

也就是说：**接口层完全兼容，坏的是生命周期**。

## 故障

```
RemoteError: agent-preset/not-found  Unknown agent preset: dsh-stack
  at AgentPresetRegistryService.resolve (dsh-agent-preset-registry/lib/index.js:612)
  at SessionController.create        (dsh-api-session-controller/lib/index.js:269)
```

机制是三处合理行为的叠加：

1. `selectedDefault` 只在用户换预设时写入（`dsh-client-ui-agent-preset/lib/client.js:1666`），落在 profile 的 `cordis.patch.yml`。
2. 停用 bundle 只删 `dsh.profile.bundles` 的项（`dsh-plugin-manager/lib/index.js:3048-3080`），卸载只 `pnpm remove` 目录 —— **都不碰这个指针**。
3. 新建会话入口没有兜底：`presets.resolve(presetId)` 抛错即失败。前端只有 `restoreBlank()`（`dsh-client-ui-workspace/lib/client.js:1455-1474`）捕获这个错误，而它服务的是空白页恢复，不是新建。

用户视角：装过这个插件之后，整个应用新建不了会话；卸载也不会自己好。

## 本次做法

三层，各管一种时机（设计取舍见 `docs/decisions/06-卸载守卫挂在-profile-根.md`）：

1. **`preset/uninstall-guard.mjs`** —— 挂在 profile 根（不是预设里），加载时对账一次，并用 `ctx.effect` 的 disposer 在 fiber 销毁前收一次。判据是磁盘状态（包在不在 / bundles 有没有 / 补丁有没有 `disabled`），所以正常退出时**一个字节都不改**；停用/卸载时宿主先写盘再 reload，它才动。
2. **`bin/dsh-stack.mjs`** —— `status` / `doctor [--fix] [--sessions]` / `uninstall`。卸载命令坚持「先收指针再删包」，并把上次手工清的那六处残留全部自动化。
3. **备忘录 `.dsh-stack-guard.json`** —— 收指针时记下「是我收的、收成了什么」，插件重新可用后恢复用户原本的选择；用户期间换过预设则不覆盖。

## 验收

```bash
npm test                      # 79 条断言 + 五个校验脚本
node bin/dsh-stack.mjs status # 每个 profile 的可用性与指针状态
DSH_ROOT=<解包的宿主> node scripts/verify-host-api.mjs   # 9 项契约
```

真实 cordis（4.1.0）下的三个生命周期场景实测：

- 正常退出（包在、bundles 在）→ dispose 后 `cordis.patch.yml` **未变**；
- 停用（bundles 被删）→ dispose 后 `selectedDefault: standard`，备忘已写；
- 重装 → 加载后 `selectedDefault: dsh-stack` 恢复。

另外抓到一个装不上而不是用不了的坑：bundle 补丁的 `insert[].name` 以 **patch 文件所在目录**为基准重写（`dsh-app-boot/lib/index.js:4718-4725`），而 `cordis:include` 的 `config.path` 运行时按 profile 目录解析。守卫行因此写 `./preset/uninstall-guard.mjs`。这是合成验证出来的，静态读代码看不出来。

## 教训

1. **清残留 ≠ 修机制**。上一轮把机器恢复到了「干净的已卸载」状态，症状消失，但「停用即悬空」的机制原样保留 —— 用户只要再装一次、再停一次，故障一模一样。判断一次修复是否完成的依据，是**复现步骤还在不在**，不是现场干不干净。
2. **归因要给「升级」以外的假设同等的预算**。这次的真正变量是「装上之后停用了」，而不是「升级到 0.2.2」。先跑接口契约（快、便宜、能一票否决），再回到生命周期。
3. **插件侧的自救位置由失败时机决定**。崩溃发生在会话创建之前，所以修复必须挂在比预设活得更久的位置（profile 根、disposer），否则永远不会被激活。这一条比任何实现细节都重要。
