# 实现说明

给维护者看：这个 bundle 由哪些文件组成、每个文件为什么是这样、依赖宿主的哪些私有契约、怎么验证。

用户视角的说明在 [README.md](../README.md)，本文只写实现层。

## 一、装载链路

一次安装到生效要经过四步，任何一步断掉的表现都是「预设列表里没有它」：

```
profile/package.json
  └─ dsh.profile.bundles: ["dsh-stack"]
      └─ node_modules/dsh-stack/cordis.patch.yml      ← dsh.bundle.patch 指向这里
          ├─ insert: preset-dsh-stack（@deepseek-ai/dsh-agent-preset）
          │   └─ plugins[0]: cordis:include
          │       └─ ./node_modules/dsh-stack/preset/agent.cordis.yml
          │           └─ 预设内部的全部行
          └─ insert: st-stack-uninstall-guard（./preset/uninstall-guard.mjs）
              └─ 生命周期守卫，挂在 profile 根（不是预设内）
```

**关键约束：两处相对路径的基准不同，混用就装不上。** 这是本仓库最容易写错的一条，实测确认过：

- **`insert[].name`** 以 **patch 文件所在目录**（即包目录 `node_modules/dsh-stack/`）为基准，被 `anchorInsertedPluginNames` 重写成 `file://` URL（`dsh-app-boot/lib/index.js:4718-4725`）。所以守卫行写 `./preset/uninstall-guard.mjs`；写成 `./node_modules/dsh-stack/preset/...` 会变成 `<包目录>/node_modules/dsh-stack/preset/...`，多一层，加载即失败。
- **`cordis:include` 的 `config.path`** 不被上述重写处理，运行时由 `new URL(config.path, baseUrl)` 解析，`baseUrl` 是 profile 目录。所以 include 必须写成「从 profile 根出发、穿过 node_modules」的形式：

```yaml
path: "./node_modules/dsh-stack/preset/agent.cordis.yml"
```

进了 `preset/agent.cordis.yml` 之后，`baseUrl` 变成该文件自己的目录，于是 `./st-loop.mjs` 与 `./skills` 都能在旁边解析——这是 link 安装（symlink/junction）也能正确工作的原因。

`scripts/verify-preset.mjs` 交叉校验这两条：include 路径 == `./node_modules/${package.json name}/preset/agent.cordis.yml`，守卫路径 == `./preset/uninstall-guard.mjs`，且两者在仓库内都真实存在。

## 二、文件职责

### `cordis.patch.yml`

只做一件事：插入一条 `@deepseek-ai/dsh-agent-preset` 声明行。

| 字段 | 值 | 为什么 |
|---|---|---|
| `id` | `preset-dsh-stack` | 宿主按 id 去重；改名等于换一个预设 |
| `config.id` | `dsh-stack` | 会话选择器里存的值，`preset.test.mjs` 断言它没变 |
| `config.name` | `dsh-stack模式` | 用户看到的显示名 |
| `config.order` | `6` | 与内置预设的排序错开；改它只影响列表位置 |
| `config.description` | 一段中文 | 选择器里的副标题 |

### `preset/agent.cordis.yml`

按注释分段：identity / instructions / loop guard / shell / filesystem / jobs / skills / goals / plan / compaction / delegation / remaining rows。

三处与 `standard` 预设**不同**，其余逐行一致：

1. `persona.prefix` — 把 `st-mode` 的规则压成常驻人格。`complete` 保持 false：本包只改「怎么工作」，不删掉工具指引、运行时上下文、审批与沙箱提示。
2. `st-loop` — 多一行守卫插件。
3. `skill-filesystem.customSkillDirs` — 追加本包的 `./skills`。

### `preset/st-loop.mjs`

监听 `agent/turn-stopping`，读本轮事件，命中规则就 `steer` 一条消息。逻辑细节见文件头注释与 README 的「两个守卫」；这里只记维护要点：

- `analyzeTurn()` 把本轮事件归约成三个事实：`evidenceMissing`、`failStreak`、`mutatedFiles`。
- `mutatedFiles` 只收「最后一次成功检查之后」的改动——更早的改动已被证明，列出来会让模型去查不需要查的文件。
- `claim()` 按 `${session.id}:${turn}` 记账，返回本次是第几次打回；第二次用更硬的措辞。
- 任何异常走 `warnOnce` 后返回，绝不阻断轮次收尾。

### `preset/uninstall-guard.mjs`

本包唯一会写用户 profile 的代码。它解决的是一个生命周期缺口，不是预设功能：用户把本预设设为默认后，停用/卸载不会清理 `selectedDefault` 指针，下一次新建会话在 `presets.resolve()` 抛 `agent-preset/not-found`，而那条调用路径没有兜底。

行为两条，判据都是**磁盘状态**（包在不在 / bundles 有没有 / 补丁有没有 `disabled`）：

- `apply()` 里对账一次：不可用而指针指着自己 → 收回 `standard`；
- `ctx.effect(() => cleanup)` 的 disposer：fiber 销毁前再收一次（停用、卸载、热重载都走这条路径）。

正常退出时三项全真 → 一个字节都不改。收指针时留 `.dsh-stack-guard.json` 备忘，插件重新可用后恢复用户原值（用户另选过则不覆盖）。完整取舍见 `docs/decisions/06-卸载守卫挂在-profile-根.md`。

### `preset/lifecycle.mjs`

守卫与命令共用的纯函数库，零依赖、无宿主 API：

| 函数 | 用途 |
|---|---|
| `resolveDshHome()` / `listProfiles(home)` / `inspectProfile(profile)` | 定位 `~/.dsh`、枚举 profile、判定可用性 |
| `readSelectedDefault` / `rewriteSelectedDefault` | 从 patch 文本里读写那一个标量，不解析、不重排整个 YAML |
| `patchDisablesPreset` | 预设行是否被 `disabled: true` |
| `repairProfile` / `restoreProfile` / `clearDanglingPointers` / `restorePointers` | 单 profile 与跨 profile 的收/还 |
| `forceClearPointer` | 卸载专用：不看可用性，直接收（必须在删包之前） |
| `editProfileManifest` | 结构化编辑 profile 的 `package.json`，只在真变化时写盘 |
| `pruneProjections` / `pruneProjectionFile` | 投影缓存里 `agentPreset.val` 的降级，只认这个精确形状 |

### `bin/dsh-stack.mjs`

`status` / `doctor [--fix] [--sessions]` / `uninstall` 三个子命令。守卫够不到的两种场合由它兜：宿主已经崩过、或者用户直接删目录而没走停用流程。`uninstall` 的顺序是硬要求——**先收指针再删包**，反过来就留下崩溃窗口。

### `preset/skills/`

29 个技能，正文逐字来自技能来源，标识已改名（`ds-*` → `st-*`）。**本仓库不改写任何散文**——这是「跟上游覆盖目录 + 重跑改名即可同步」的前提。需要本地改造时先改上游。

## 三、依赖的宿主私有契约

守卫依赖四个不在公开文档里的接口。`scripts/verify-host-api.mjs` 会逐条断言它们还在：

| 契约 | 位置 | 断了会怎样 |
|---|---|---|
| `agent/turn-stopping` 在轮次收尾被 `dispatch.serial` | `dsh-agent-loop/lib/index.js` | 守卫永不触发，完全静默 |
| 该钩子的载荷里由 `agentEvents` 注入 `agent` | `dsh-agent/lib/types/dispatch.js` | `agent` 为 undefined，守卫第一行就 return |
| `agent.steer(input)` 语义是 `send(input, "next-step", true)` | `dsh-agent-loop/lib/index.js` | 消息进错队列，轮次不会继续 |
| `session.snapshotEvents()` 返回持久事件数组 | `dsh-session/lib/index.js` | 读不到本轮事件 |

还有一条不归守卫管、但同样致命的人格契约：

| 契约 | 位置 | 断了会怎样 |
|---|---|---|
| 提示词里只能出现宿主注册过的 `{{变量}}`，目前只有 `provider` 与 `model` | `dsh-agent-loop/lib/index.js:1607-1608` 注册；`dsh-system-prompt/lib/index.js:174` 抛错 | 写错一个变量名，`deployment:persona-suffix` 每次渲染都抛 UNKNOWN，**会话启动即死**，模型一步不跑。0.1.0 就是死在这里 |

这条没有降级路径，也不能靠「跑一次就知道了」来发现——会话连第一步都到不了。`verify-host-api` 第 6 项从 `dsh-agent-loop` 源码里抓出注册调用再比对；`test/preset.test.mjs` 有同一断言的独立版本，白名单硬编码，因为 CI 上没有 DSH 安装。

另外两条**静默失效**风险：

- `mutationTools` / `checkTools` 里的工具名必须等于宿主实际注册的名字。宿主给工具改名，守卫照常运行，只是永远匹配不上。校验脚本会读 `dsh-tool-fs` / `dsh-tool-bash` / `dsh-tool-pwsh` 的注册表比对。
- **`ctx.effect` 的 disposer 必须在 fiber 销毁时执行**。卸载守卫的全部价值压在这条上：`effect(execute, label)` 收集返回值，fiber 销毁时逆序执行（`@deepseek-ai/cordis/lib/index.js:463` 起）。宿主换掉这套收集器，守卫不会报错，只会在离开时静默失效——而那是它唯一该起作用的时刻。`verify-host-api` 第 7 项断言 `effect(` / `runDisposable(` / `_disposables.delete(` 三处仍在。
- **`selectBundle` 不碰 `selectedDefault`**。这是守卫存在的前提。宿主哪天补上这一步，守卫变成多余（无害），但 README 与决策文档里的机制描述就该更新；`verify-host-api` 第 8 项会在 `selectBundle` 体内出现 `selectedDefault` 时失败，逼我们回来看一眼。
- **投影缓存的形状**：`~/.dsh/storages/session_projcache/sessions/<uuid>.json` 与 `~/.dsh/sessions/<workspace>/projcache.json`，预设记在 `record.rows.agentPreset.val`。守卫的 `--sessions` 只改这一个字段，正文与标题是用户数据，一个字不动。
- `session.snapshotEvents()` 在宿主里已标记 `@deprecated`（新调用被禁止），当前仍可用，替代 API 尚不存在。升级到移除该方法的版本时，守卫必须迁移到投影或分页读取。这是本包最可能需要跟进的一处。

## 四、验证

```bash
npm test                                   # 79 条断言 + 6 组脚本校验
node scripts/verify-release.mjs            # 发布前置（prepublishOnly 自动跑）
npm run verify:release -- --verify         # 发布后三方对齐
```

`verify-mount.mjs` 与 `verify-host-api.mjs` 都需要一份 DSH 安装：两者在没装的机器上（CI）打印 SKIP 并退出 0——这两个判据只在装了 DSH 的机器上有意义。

`verify-mount.mjs` 存在的理由是「字符串写对了 ≠ 解析对了」。它把包按真实安装形态铺进临时 profile（`node_modules/dsh-stack` 用符号链接指回仓库根，顺带覆盖 link 安装），再交给宿主自己的 `loadProfileDirectory` 合成，最后断言守卫行的 `name` 已被 anchor 成 `file://` URL 且落在包目录下、include 仍按 profile 目录解析且目标存在、三处 id 一致。**改 `cordis.patch.yml` 里任何一条相对路径后必须跑它** —— 这两处基准不同，写错的表现是加载失败，静态断言看不出来。

## 五、已知限制

1. **`bash` 可绕过「改完没验证」**：一条 `bash` 同时写文件并跑命令时只算验证。取舍原因见 README。
2. **守卫没有跨轮记忆**：`failStreak` 只看本轮末尾。跨轮次的「同一个修法错三次」不会被识别——需要读多轮事件，成本与收益不匹配。
3. **技能目录是固定前缀成本**：6830 字符 ≈ 1708 token，每轮重发。删目录是唯一无损的减法。
4. **`snapshotEvents` 是弃用接口**（见上）。
5. **预设只在空白新会话可选**：宿主限制，不是本包能改的。
6. **守卫依赖一次执行机会**。它在 fiber 销毁时生效，覆盖「停用/卸载/重载」；但用户在宿主**已经退出**之后再 `rm -rf node_modules/dsh-stack`，守卫没有机会运行。这种场合只能靠 `npx dsh-stack doctor --fix`，README 的「停用与卸载」表里写明。
7. **崩溃点本身在宿主**。新建会话的 `presets.resolve()` 没有兜底（`restoreBlank()` 只服务空白页恢复）。本包做的是「不让指针悬空」，不是「让悬空指针无害」；后者需要宿主改动，超出本包边界。
