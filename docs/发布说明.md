## 0.3.0 — 2026-11-06

### 为什么接这一版

用户报：DSH 升级到 `0.2.2-rc.1` 后，装本插件出现异常。

先做的是排除法，结论是**接口层完全兼容**：`engines.dsh >=0.2.1-rc.5` 满足、预设引用的 25 个 `@deepseek-ai/*` 包零缺失、`verify-host-api` 7 项全 PASS、宿主内 cordis `4.1.0` 满足 peer `>=4.0.5`。日志里那条 `desktop welcome: Web authentication failed` 是 0.2.1-rc.3 时期就有的桌面端遗留，与本次无关。

真正的原因在**生命周期**，而且上一轮排查（会话 `session-19333a62`）已经定位过同一个问题 —— 但那次修的是现场：手工清了六处残留、改了 11 个会话档案与 23 份投影缓存。机制没动，所以只要用户再装一次、再停一次，故障一模一样。

机制是三条合理行为叠加出来的：

1. 「当前默认预设」只在用户切换预设时写入 profile 的 `cordis.patch.yml`（`dsh-client-ui-agent-preset/lib/client.js:1666`）；
2. 停用 bundle 只删 `dsh.profile.bundles` 的项（`dsh-plugin-manager/lib/index.js:3048-3080`），卸载只 `pnpm remove` 目录 —— 都不碰这个指针；
3. 新建会话入口 `presets.resolve(presetId)` 抛 `agent-preset/not-found` 即失败，那条路径没有兜底。

于是「装过这个插件」变成「整个应用新建不了会话」，卸载也不会自己好。

### 改了什么

三层，各管一种时机：

| 层 | 位置 | 管的时机 |
|---|---|---|
| 卸载守卫 | `preset/uninstall-guard.mjs`，由 bundle 补丁挂在 profile 根 | 加载时对账、`ctx.effect` 的 disposer 在停用/卸载/重载时收指针 |
| CLI | `bin/dsh-stack.mjs`（`status` / `doctor [--fix] [--sessions]` / `uninstall`） | 宿主已经崩过、或用户直接删目录没走停用流程 |
| 备忘 | `.dsh-stack-guard.json` | 记住「是我收的、收成了什么」，插件回来时恢复用户原值 |

判据是**磁盘状态**（包在不在 / `bundles` 有没有 / 补丁有没有 `disabled`），不是内存状态：正常退出时三项全真，守卫一个字节都不改；停用/卸载时宿主先写盘再 reload，它才动。这条有专门测试。

**没有一个方案是 Web 按钮**，尽管用户提了这个选项：按钮活在插件里，而它唯一该起作用的时刻恰好是插件已经不在了。要做只能做成宿主侧功能，那超出本包边界。

### 复现与验证

```bash
npm test                                   # 79 条断言 + 六组校验脚本
node bin/dsh-stack.mjs status
node bin/dsh-stack.mjs doctor --fix
DSH_ROOT=<解包后的宿主> node scripts/verify-host-api.mjs    # 9 项
```

真实 cordis（宿主内的 4.1.0）跑了三个生命周期场景：正常退出（文件未变）/ 停用（指针收回 `standard` + 备忘已写）/ 重装（恢复 `dsh-stack`）。

端到端合成验证另外抓到一个**装不上**（不是用不了）的坑：bundle 补丁的 `insert[].name` 以 patch 文件所在目录为基准重写成 file URL（`dsh-app-boot/lib/index.js:4718-4725`），而 `cordis:include` 的 `config.path` 运行时才按 profile 目录解析。所以守卫行写 `./preset/uninstall-guard.mjs`，include 写 `./node_modules/dsh-stack/preset/agent.cordis.yml` —— 混用会多一层 `node_modules/`，加载即失败。静态读代码看不出这条，只能靠 `loadProfileDirectory` 实跑。

### 已知遗留

- **崩溃点本身在宿主**。新建会话的 `presets.resolve()` 没有兜底（`restoreBlank()` 只服务空白页恢复）。本包做的是「不让指针悬空」，不是「让悬空指针无害」。后者需要宿主改动，建议给 DSH 提 issue。
- **守卫依赖一次执行机会**。宿主已经退出之后再 `rm -rf node_modules/dsh-stack`，守卫跑不了，只能 `doctor --fix`。README 的处境表写明了这一点。
- `verify-host-api.mjs` 在 CI 上恒为 SKIP（CI 没有 DSH 安装），宿主契约实际只在维护者本机校验。这是既有状况，本次未改。

## 0.2.0 — 2026-11-04

破坏性改名：29 个技能的手势 `ds-*` → `st-*`，预设 id `ds-stack` → `dsh-stack`。按「用户可感知的行为变化」定级为 **minor**，不是 patch：用户记住的 `/ds-tdd` 全部失效。

### 为什么接这一版

本机和用户机器上都可以同时装 `dsh-ds-stack-preset` 与本包。两者的 29 个技能逐字节相同、名字也相同（都叫 `ds-*`），预设 id 也同为 `ds-stack`。并存时：技能列表出现两套同名条目，选择器里两个一模一样的 id，`/ds-help` 命中的是哪一个只能翻 `node_modules`。

这不是美观问题，是可判断性问题。上一轮已确认本机`dsh-ds-stack-preset` 彻底卸载（`node_modules` 无该目录、lockfile 零引用、bundles 只有 `dsh-stack`、`.agent-presets` 只有 `redteam`/`unrestricted`），但那只是本机状态，用户装两个包时问题依旧。

## 0.1.2 — 2026-11-04

只改文档，但 README 进包，所以要升版本。

### 为什么接这一版

0.1.0/0.1.1 的 README「用法」只有三行：选预设、首轮带技能目录、`/st-help`。信息没错，但对第一次用的人是无效的——看完仍然不知道第一句该说什么、看到 `st-stack checkpoint — …` 时该不该慌、29 条技能里现在该点哪条。

这次把这一章扩成五章，核心是四个问题的答案：

| 问题 | 落在哪 |
|---|---|
| 第一句该说什么 | 快速上手里的「目标 + 约束 + 验收标准」与正反例 |
| 现在该点哪个技能 | 五组场景索引表 |
| 它写的这个 checkpoint 是报错吗 | 例 2，附守卫原文与三点解释 |
| 哪些用法会白费力气 | 技巧 7 条 + 反模式 5 条 |

### 为什么必须升版本

`README.md` 与 `README.en.md` 在 `package.json` 的 `files` 白名单里，属于进包内容。铁律要求「tag 之后进包内容不得变化」，所以 `verify-release.mjs --verify` 直接拦了：

```
- tag v0.1.1 之后有 2 个进包文件变化：README.en.md、README.md
  → 进包内容变了就必须升版本、重新打 tag
```

这是门禁按设计工作的样子，不是要绕过的障碍。纯文档改动升 patch。

### 写的时候守住的几条

- **例 2 的文案逐字取自 `preset/st-loop.mjs:179` 的 `evidenceText`**，不是手写模拟。README 里贴假消息，用户拿去对照就会以为守卫坏了。
- 技能表只写「处境 ↔ 手势」，不复制 29 条 description——那些每轮已经作为技能目录进上下文，README 再存一份只会两边一起过期。
- 技巧 5 明确写「觉得贵就删目录，别调 `catalogDescriptionMaxLength`」，因为上游把 `Use when …` 放在描述末尾，截断先丢触发条件。
- 反模式第一条承认 `bash` 一把梭绕得过第一条守卫。这是有意的取舍（否则 `sed -i && npm test` 会误报），文档里不粉饰。

### 复现

```bash
node scripts/verify-release.mjs --verify   # 改 README 不升版本 → 1 项失败
npm version 0.1.2 --no-git-tag-version
npm test                                   # 13 + 17 断言 + 4 组脚本校验
grep -c "^## " README.md README.en.md      # 13 13，章节键集合一致
```

### 已知遗留

中英两版是人工对齐的，没有脚本检查章节键集合。目前靠 `grep -c "^## "` 比对数量，数量相同但标题错配不会报警。等中英版本再增一章时补一条检查。

## 0.1.1 — 2026-11-04

修一个会让 0.1.0 直接不可用的缺陷，并把这类缺陷变成提交前就能拦住的东西。

### 为什么接这一版

0.1.0 从上游原样继承了 `persona.suffix: Your working directory is {{cwd}}.`。宿主（`dsh-system-prompt/lib/index.js:174`）遇到未注册的变量不降级，直接抛：

```
unknown prompt variable "{{cwd}}" in section "deployment:persona-suffix";
registered variables: provider, model
```

结果是**选了「dsh-stack模式」的会话启动即死**，模型一步都没跑。这个错误是逐个 turn 抛的，会话看起来建起来了，实际什么都没发生。

变量注册点只有两处，都在 `dsh-agent-loop/lib/index.js`：

```js
1607  ctx.systemPrompt.variable("provider", (context) => context.agent?.options.provider)
1608  ctx.systemPrompt.variable("model",    (context) => context.agent?.options.model)
```

内置 standard 预设（`@deepseek-ai/dsh-web-app/presets/standard.patch.yml:11-14`）只有 `prefix: ""`，没有 suffix——上游那句是凭印象加的。

### 连带改动清单

| 类别 | 文件 | 说明 |
|---|---|---|
| 修复 | `preset/agent.cordis.yml` | 删掉 `suffix:` 行；人格注释块改写为记录「为什么不能有 suffix」 |
| 新增 | `scripts/verify-host-api.mjs` | 第 6 项检查：从 `dsh-agent-loop` 抓出宿主注册的变量名，比对预设里用到的 `{{…}}` |
| 新增 | `test/preset.test.mjs` | 同一条断言的独立版本，白名单硬编码 `provider`/`model`，CI 里也能跑 |
| 变更 | `package.json` | 0.1.0 → 0.1.1 |

### 为什么这条断言要写两遍

`verify-host-api.mjs` 在找不到 DSH 安装时打印 SKIP 并 `exit 0`——这是对的，它检查的是宿主私有契约，没有宿主就没法查。但**CI runner 上没有 DSH**，所以这条最关键的检查在 CI 里等于不存在。

`test/preset.test.mjs` 是纯 node 断言、零依赖、不需要宿主，把宿主当前注册的两个变量名硬编码进去。代价是宿主新增变量时要手动同步；好处是这条检查在每一台跑 `npm test` 的机器上都真实生效。

### 守卫的三处行为变化

**1. 打回文案只列未证明的文件**

上游 `analyzeTurn()` 从 `0` 扫到 `lastMutation`，把所有改动过的文件都塞进文案。问题：本轮先改 A、跑了检查、再改 B，文案会把 A 也列出来，指向已经处理完的目标。

改为从 `lastCheck + 1` 扫到 `lastMutation`。复现（`analyzeTurn` 不导出，走真实钩子契约，与单测同构）：

```bash
node --input-type=module -e "
const mod = await import('./preset/st-loop.mjs')
let seq = 0
const call = (id, name, args) => ({ type: 'tool/call', seq: seq++, data: { turn: 1, step: 1, callId: id, name, arguments: JSON.stringify(args) } })
const res = (id) => ({ type: 'tool/result', seq: seq++, data: { turn: 1, step: 1, message: { toolCallId: id, isError: false } } })
const events = [
  call('1', 'edit', { file_path: 'a.js' }), res('1'),
  call('2', 'bash', { command: 'npm test' }), res('2'),
  call('3', 'edit', { file_path: 'b.js' }), res('3'),
]
let steer
mod.apply({ on: (n, h) => { if (n === 'agent/turn-stopping') steer = h }, logger: { warn() {} } }, {})
steer({ turn: 1, agent: { session: { id: 'demo', header: {}, snapshotEvents: () => events }, steer: (m) => (steer.msg = m) } })
console.log(steer.msg.content[0].text)
"
```

文案里应只出现 `b.js`——`a.js` 已被第 2 步的检查覆盖，上游会把它也列出来。

**2. 工具名收窄**

上游默认值里有 `str_replace_editor` / `apply_patch` / `multiedit` / `notebook_edit` / `sh` / `shell`，本机宿主一个都没有。实测注册表：

```bash
grep -o '"[a-z_]*"' "/Applications/DeepSeek Harness.app/Contents/Resources/app/dsh/node_modules/@deepseek-ai/dsh-tool-fs/lib/index.js" | sort -u
```

改为 `[write, edit]` / `[bash, pwsh]`。`verify-host-api.mjs` 会读宿主注册表逐项比对，宿主改工具名时直接 FAIL。

**3. 单轮打回上限 1 → 2，第二次更硬**

上游 `maxSteersPerTurn: 1`。问题是：模型无视第一次打回、照样结束轮次时，守卫彻底沉默——而这恰好是最需要再说一次的情形。

改为 2，且 `evidenceText(mutatedFiles, attempt)` 在 `attempt > 1` 时返回第二版文案（含 "You are closing the turn without evidence a second time"）。限次仍在，不会成环。测试用例 `second nudge is worded harder` 覆盖。

### 已知遗留

1. **`session.snapshotEvents` 已标 `@deprecated`**。宿主 `dsh-session/lib/index.js:1454` 的注释写着「现有逻辑可暂不迁移，但禁止新增生产调用」，而替代 API 尚不存在（`ownEvents()` 也弃用，且语义不同）。守卫暂用，升级宿主到移除该方法的版本时必须迁移。`verify-host-api.mjs` 的 D4 会先失败，不会静默。
2. **技能目录固定成本 6830 字符 ≈ 1708 token/轮**。未做分级加载：29 条全留是按批准的取舍，删目录是唯一无损减法。
3. **`bash` 可绕过「改完没验证」**。一条 `bash` 同时写文件并跑命令时只算验证。取舍原因见 README「边界与注意」。
4. **守卫无跨轮记忆**。`failStreak` 只看本轮末尾，「同一个修法错三次」跨轮识别不到——需要读多轮事件，成本与收益不匹配。
